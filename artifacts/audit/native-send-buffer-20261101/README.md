基线 `16cb4cec`（AAD已复用的node `dbb81a9c…`），候选 `a524ab3f…`。
不是再与旧v4比较，也没有把上一轮AAD收益算入本轮。
沿原 `NativeObjectSender → NativeUdpSession::encode → E2eSecureChannelV1` 改造，
不改协议、nonce/tag/AAD、完整性、重放、补片、配额、线程、账户、AOEM、GPU或共识。

后续[当前发送成本基线](../native-send-cost-baseline-20261101/README.md)直接测本页冻结

性能结果，不把新的诊断负载当作持续性能提升。

## 1. 原调用链的工作量审计

| 原步骤 | 本轮处理 | 边界 |
| --- | --- | --- |
| 原对象分片生成payload Vec | 保留 | 不是本轮消除的分配 |
| Frame::new及编码checksum | 保留 | Frame字段可变，编码必须刷新，不能直接信缓存 |
| seal克隆两个peer-id String | UDP wire路径消除 | 通用envelope消费者仍需要其原所有权 |
| 独立plaintext/ciphertext Vec | UDP wire路径消除 | 直接在最终wire的明文后缀中加密 |
| binary::encode再分配wire并复制整份ciphertext | UDP wire路径消除 | 最终wire本身的一次分配保留 |
| Windows分段批发拼接Vec及复制 | 保留 | 已接上批发，不是未启用，也没有声称零复制 |
| sendto及Windows回环交付 | 保留 | 之前ETW的回环份额不等于真实网卡成本 |
| owned接收复用输入Vec | 原本已实现，未改 | 不算本轮新成果 |

具体删掉的是该UDP封装内**两次String克隆、一份独立密文Vec，以及密文→wire搬运**。
按源码分配点是四份输出/中间分配变为一份最终wire，不是全局allocator事件计数，
不是每笔交易总分配数，也不减少独立签名、协议字节或必需的数据报数。

## 2. 薄接线，不另写网络或编码器

原binary codec抽出共享的借用Header写入与完整长度预检；原envelope encode也调用它。
最终Vec先写原NVRLY002字段，再调用原frame::encode_into追加规范明文；
原会话使用同一ChaCha20-Poly1305实现对明文后缀计算detached tag并追加16字节。
envelope API与直接wire API共享原发送序号推进和AEAD运算函数，没有第二套密码算法。

UDP入口仍先检查inner session和payload。通用envelope调用方及Bound可靠carrier保留
原合同；这是原UDP编码实现替换，不是新的产品入口、备用协议或WSS迁移。
最终wire预留完整容量，调试断言检查追加规范帧和tag时没有扩容。
精确limit拒绝仍与旧路径一样消耗已分配的发送序号，MAX耗尽不推进；不复用认证结论。

新增测试逐字节对照同key/session/nonce/Frame输入，覆盖双向、Data/Repair、空/短/长payload、
可变Frame后checksum刷新、精确limit失败/后续发送、序号耗尽和原重放拒绝。
原binary固定布局独立向量与原AAD/密码参考继续检查，不能只由两个相同新helper互证。

## 9. 结论与剩余阻断

**实现成立：原UDP最终wire里就地完成原帧封装，少了确定的分配与复制；
局部准备中位耗时减少约3.1%–5.3%，安全和原进程恢复范围通过。**

**整链稳定提速不成立：两组同字节表现不一致，持续组有负向，入口CPU未稳定下降。
4K未达到，12K未恢复；性能任务仍未完成。** 保留为减少重复工作的开发候选，
不是正式库或部署资格，也不以“接口接通”“922项通过”替代性能签收。

剩余原路径工作已在第1节区分：原payload分配、帧checksum、真实逐包AEAD、
Windows批发拼接及内核/回环交付仍在；批次短尾之后的未提交封装也仍可能有浪费。
本轮未修改它们，未量得它们在新候选上的各自占比，不再推算下一改动必达4K。
状态捕获、补片、公钥分布和候选阶段没有顺便调参，不把未解决慢轮次自动结案。

Linux、真实多机、默认并发/WSS、完整候选CI和制品能力匹配仍是独立门禁。
main、正式随包库、部署、Auto、既有数据库/journal和受保护知识库均保持不动。
