# 原输入投递责任与补送优先级修复

本轮从 `ae5436af` 开始，在 `dev/mldsa65-identity-closure` 修复一处已复现的原 gossip 调度缺陷。
**旧补送被保留的新批次抢占的窗口已修复；吞吐没有证明稳定改善，12K 恢复任务仍未完成。**
不改账户模型、ML-DSA、nonce、法定门槛、生产超时、APFL 容量、socket 或预取策略。
main、正式 AOEM 随包库和部署均未改变。

## 原扇出为何需要补送

`gossip_missing` 表示原输入扇出在本机没有给该 peer 预留投递，不表示 UDP 丢包。
原 `NativeLifecycle` 每 peer 最多保留两个输入投递句柄；完整接收的 DONE 返回后才释放。
输入投递没有高度／轮次窗口，不会仅因推进高度而被当作过期实时票取消。

16384 笔诊断样本抓到以下真实窗口：

1. node0 的 scope31 因 node2 的两个输入槽位已满而略过该 peer。
2. 随后预备的 fresh offer 在没有可用槽位时被原 RPC owner 保留。
3. 槽位重新开放时，代码直接提交保留的 fresh，绕过 `prefer_repair=true` 的既有选择规则。
4. scope33／34 先取得槽位；与 scope31 相同有序1024行组到 scope39 才获补送准入。

省略到补送预留为 **1591.093 ms**；这是本轮对象的本地责任证据，不能追溯证明旧 h40 已淘汰对象的全部行为。
完整 scope、fragment、peer、占槽对象和预算见[修复前分析](analysis-before-qualified.json)。

修复只在原 `RpcLifecycle::poll_gossip` 增加一次选择复核：优先补送重新可用时，
尚未交给传输 owner 的 fresh 行按原顺序归还原 deque，再走现有 repair selector。
保留 `gossip_queued` 去重、原签名字节和池记账；已退役行不复活，不取消在途发送。
补送之后仍轮到 fresh，未增加队列、线程或资源上限。

真实 ML-DSA 准入／原 UDP-DONE 反例在旧调度下失败：预期补送次数1，实际0。
修复后两项反例通过，包含新旧交替、行顺序、原 Arc／字节、退役及资源记账。
见[旧失败](retained-offer-old-fail.log)、[修复通过](retained-offer-fixed.log)。

实际 carrier 写入不是对端收到，Repair 写入数量也不是物理丢包数量。
这份证据排除了该对象末尾哈希／解码的秒级等待，尚未分清发送/接收调度、实际丢弃和补片策略的贡献。
哈希可能与收片重叠，不能将其跨度当成 CPU 计算时间，也不能将阶段跨度相加。

沿已有 `NativeTransferDiagnosticsV1` 记录，默认关闭，仅筛选原 NVINPUT1 流，仍为256条／120秒；
现有 asset ring 仍为8192条。初发／补发／Probe 只在 carrier 实际写入成功后计数。
不记录私钥或完整签名，不参与准入／授权／共识。
同 tag 发送重试按 attempt 重置发送记录；跨 attempt 精确阶段不可用。
接收 TTL 重建尚未单独分代，不能把跨重组代次的合并记录当成精确单次时间。
开启观察器存在额外开销；以下性能测试全部关闭诊断。
