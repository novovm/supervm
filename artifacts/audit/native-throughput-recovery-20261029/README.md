# 原资产账户路径持续在途压测与吞吐恢复

## 结论

**本轮未恢复 12K TPS，性能任务不通过。** 已落实简洁实现规则，修复池满丢弃合法输入等实际问题，并恢复 8,192 笔上限的持续在途负载。最终候选完成三轮 65,536 笔及冷恢复，但 CPU 只有 1,152／1,204 TPS，GPU-required 为 1,525 TPS；同字节 4,096 笔对照还出现 CPU 回退。

本提交是开发分支检查点，不是性能优化签收或发布候选。`main`、正式随包 AOEM、部署和已有数据保持不动。数字、源码文件 SHA-256、实际库与程序身份、测试摘要见 [evidence.json](evidence.json)。

## 原路径和实际修改

原 node tick → NovoRUDP/APFL → RpcLifecycle 严格准入池 → NativeLifecycle／CandidateBodies → CandidatePipeline → novovm-exec／bindings／AOEM → 原共识、ValidatorJournal、发布查询。

没有另建执行器、账户库或网络。ML-DSA-65、具体资产账户寻址、384 KiB 正文预算、1,024 行配置上限、原法定门槛、费用及签票 ACK 均保留。

| --- | --- | --- |

## 持续在途方法

复用原 `native_product_load` 的 SDK、发送、查询及真实节点驱动，新增 continuous 组织方式：初始准备 8,192 笔，此后按 256 笔有界补充，不等待整批清空。后续签名使用四节点已观察到的共同高度，保持原 256 高度有效窗口；没有扩大有效期来使压测通过。

计时从首次 native SDK 提交尝试到全部交易在四节点均被查询到最终回执，使用一条不暂停的墙钟。初始 8,192 笔签名和启动在窗外，之后签名、准备、背压和首高度等待全部在窗内。后续签名任务约 2.56–2.59 秒与客户端轮询重叠，不能从总时间扣除。

CPU／GPU 仅切换验签后端；业务后端均为 `cpu_callbacks`，AOEM、节点、查询批 128 及预算相同。显式 GPU 不允许标成 GPU 的 CPU 回退。正式测量关闭阶段诊断，未同时运行重型构建或另一个压测。

65K 三轮共享实验创世、初始根和逻辑业务，但有效期及随机化签名不同，**不是相同签名字节的 A/B**。4K 五轮才是同一个签名字节哈希。当前夹具 16 个付款方，与历史 1,024 个付款方不同；恢复持续负载方法不等于完全复刻所有历史条件。

## 与旧 12K 的具体差别

[历史验收](../native-local-overlap-20261020/README.md) 的 CPU 聚合成绩为 12,324.09 TPS，65,536 笔共 64 高度，平均 1,024 笔／块，Ed25519／V3；不是本轮 ML-DSA 实测。

现在单笔规范签名输入 5,448 字节，同一个 384 KiB 正文预算最多约 72 行。实测 54–59 行，导致相同交易量需要约 17–19 倍的确认高度。配置字段写 1,024 不表示正文还能装 1,024 笔。

这是可核对的工作量差异，不是“ML-DSA 数学慢十倍”的证明，也不是全部损失的因果分解。诊断样本中，第一个到第三个节点候选注册平均相差约 30.38 ms，第三个注册后到首个 prevote QC 平均约 2.86 ms；多数注册后等待包含其他节点尚未准备好。阶段计时嵌套，不能直接相加；原 `native_io` 计时是控制线程网络轮询，不是数据库 I/O。

本轮没有通过改确认终点、删权限、扩大正文或超时来追回数字。后续必须分别定位 CPU 回退和候选准备差异，并评审新签名体积与原组批／传播预算是否匹配；不能再承诺单靠一个并发补丁就恢复 12K。

## 保留的失败样本

- 原节点 `03105a3c…` 用新 continuous 驱动，65K 尝试在 90 秒到期：四节点各观察到 9,856 笔，已准备／发出 17,920 笔。不能把失败分母改小后当作成功 TPS。
- 中间候选 `fccc43a2…` 的 GPU 65K 尝试发生真实传输 `Expired`：955 个发送获接收、947 个完成，8 个仍在途；四节点各观察到 53,376 笔，已准备 61,440 笔。缺少过期对象 ID，尚不能定位到正文、反馈或准入。后来诊断重跑以及最终候选通过，都不能代替该负例的根因解释。
- 中间候选的诊断轮／关闭诊断轮不与最终候选混合计分。程序哈希、各轮路径、失败输出与诊断重跑见 `evidence.json` 及 [中间失败日志](final-continuous-65536-paired.log)。

## 复现与后续边界

[run.ps1](run.ps1) 调用现有 release 测试程序，设置固定候选库、原节点、业务 CPU 后端及诊断开关。最终 65K 使用过滤器 `native_asset_continuous_65536_signature_cpu_gpu_cpu`；同字节 4K 使用 `native_uca_same_corpus_bulk_authority_before_after` 并设置 `NOVOVM_NATIVE_UCA_BASELINE_NODE_BINARY` 为保留旧节点。测试程序 SHA-256 及原始报告 SHA-256 在 `evidence.json`。

原始 `report.json`、`observations.json`、四节点日志和数据库保留在所列 `target/native-product-load` 路径；Git 只保存脱敏汇总、脚本和测试日志，不提交密钥、数据库或完整本地配置。

**下一次性能资格必须先解决 CPU 负向样本及持续负载停顿，再复测，不把本检查点作为 D 的构建部署基线。** 12K 仍是未完成的恢复目标，不是上限；完整 CI 留待满足候选条件后集中执行。
