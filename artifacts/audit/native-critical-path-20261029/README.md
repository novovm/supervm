# 原生交易关键路径：候选验收与性能未达标记录

日期：2026-10-29。分支：`dev/mldsa65-identity-closure`；源码基线：`94da21e25ba4180c2193f43da9ab23dc25a59a41`。

## 结论

本轮候选的定向功能、安全和 Windows 同机四进程恢复验收通过，但**没有证明稳定性能提升，没有恢复历史约 12K TPS**。不能以本报告签性能任务完成、合入 main、更新 D 的部署包或启动真实四机链。

原实际资产账户模型、ML-DSA-65、APFL、1,024 行／8 MiB 共同容量、费用、nonce、授权预算、法定门槛和发布规则不变。没有替换随包 AOEM、部署、清库或修改 dev/test 增量编译配置。

## 已实现及删除的重复工作

详细调用链见 [IMPLEMENTATION.md](IMPLEMENTATION.md)。

1. 原计算 owner 在 ready 前完成所需验签资格检查，持有同一个 verifier；启动耗时单列，不把它隐藏成交易加速。
2. 初始状态安装／核验移到最终 I/O owner，删除服务线程临时开库、关闭后再次开库的窗口。Existing 缺失或篡改仍拒绝，未新增数据库或重试绕过。
3. Packet 热准备复用已持有的类型化计划，共用关系检查并一次生成回执投影；冷恢复仍独立解码持久字节。
4. 小的本机选批目标不再降低共同接收／执行容量；缺席节点 target=64 也能追赶 1,024 行正文。
5. 原单 Lookahead 允许本 owner durable Ready 提前准备，并沿原 AssetBody／Fanout 向其他节点交付可选后继输入。真实父 journal ACK 仍是晋升门。
6. 原交易池的完整签名凭证可被远端后继复用；重复交易退出可选复用，继续原严格路径，不将外部重复行升级成轮询错误。
7. 原恢复测试客户端的两处 backoff 设置保持一致；不改变生产 ACK、重试、TTL 或总期限。

**第 5 项尚未取得稳定提速资格。** 已记录早发逻辑字节，但收到正文、执行及确认的实际先后并未稳定形成预期重叠；不能用接线或计数替代性能证据。它仍是开发候选，不是已接受的发布优化。

## 剩余阻断和下一核验位置

1. **性能任务未完成。** 稳态和慢轮尚未恢复 12K；GPU 组件成绩与候选功能通过不改变这一结论。D 暂不据此更新部署包。
2. 4K CPU 重复轮某高度的父 ACK → 子候选耐久完成约 147–158 ms；之后 journal ACK 本身约 2 ms。候选完成事件包含准备、捕获、执行、packet、持久化，不是纯业务 CPU 运算。
3. 该负载准入每批去重约 115 键，候选加费用／政策约 157 键，非 31K 实读。31,786 是最坏容量预算，不能据此给当前等待归因。
4. 同一已确认 context 的归档仍按 peer 各自完整 recover；原 I/O owner 上有可确认的重复工作，但累计耗时不能直接解释某个高度。下一项只核验原 per-peer 已验证材料的复用与逐次等待，不新建账户库／全局缓存，不跳过冷解码验证或取消各 peer 投递责任。
5. 新早发正文的额外传播成本与实际远端重叠尚未收口；不能因源码接通就签提速。CPU 重复诊断轮只有两个 local next-leader 启动后继，全部 `completed_before_parent=0`；6 份早发逻辑责任合计 20,630,310 字节。早发仍须等待发送方自己父候选 durable Ready 后再选 child、编码约 3.44 MB 并走原正文通道，未消除前面的等待。旧 `ApflEarlyBody/BindBody` 属 V3／原 controller，不是已接通的资产引用接口；本轮不扩展新 wire 冒充已有能力。
   其中 H3 在 next leader 上只比父 ACK 提前 1.921 ms 入队；另外两节点收到早正文距入队 440.742／493.337 ms，已晚于各自 H3 候选完成 289.782／347.288 ms。后台 submit 确已发生，但提前量太短、输入到达太晚；这不等于已解释候选内部约 150 ms 的全部成本。
6. 旧查询两次超时及历史约 27% CPU 退化没有自动结案；确定性丢包反例证明了测试消费者 backoff 差异，但没有历史逐对象证据可把所有超时归到这一点。
7. AOEM 其他实验／整包发布问题、身份全面迁移、Linux／真实多机、经济与正式创世门禁仍独立验收。
