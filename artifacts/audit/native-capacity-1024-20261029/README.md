# ML-DSA 原生 1,024 行容量适配与性能证据

## 结论

本轮把原 APFL / NovoRUDP 的候选、正文传播、状态捕获和持久化容量一起适配到最多 1,024 行。真实 65,536 笔已形成 **64 个高度、每高度 1,024 笔**，不是只有配置写了 1,024。低负载仍立即处理已有合法输入，不等满块。

**性能恢复仍未完成。** 持续在途 CPU / GPU-required / CPU 为 **2,325 / 1,931 / 2,559 TPS**；同签名字节、提前准备的三轮为 **2,737 / 3,098 / 2,760 TPS**。不能混用两种测量，也不能把最高值写成持续吞吐或已恢复历史 12K。

这是 `dev/mldsa65-identity-closure` 上以 `acba3b2f` 为父提交的容量检查点。未修改 main、正式随包 AOEM、部署或旧数据。当前范围仍为 Windows 同机四进程，不是四台设备或 Linux 安装签收。

## 改了什么

仍沿原 node tick → NovoRUDP/APFL → 原准入池 → CandidatePipeline → novovm-exec / aoem-bindings / AOEM → 原共识 / ValidatorJournal / 类型化查询，没有新增执行器、网络或账本。

| 原位置 | 本轮适配 | 保留的边界 |
| --- | --- | --- |
| `service.rs`、原 CLI / SDK 消费者 | 共用容量计算：1–1,024 行，每行 8 KiB，展开正文最多 8 MiB，编码消息最多 8 MiB + 128 KiB | APFL 结构共享、独立签名、具体资产账户合同不变；不是签名聚合 |
| 原 data / ingress / application lane | 以消息上限 M 计算：每 peer 4M、每 lane 总量 max(16 MiB, 16M)，原消息数和 30 秒 TTL 不变 | control lane 仍为 512 KiB 消息、2 MiB / peer、16 MiB 总量 |
| 原 Host delivery / body retention | delivery 8M / peer；body max(64 MiB, 16M)（最大配置分别 65 / 130 MiB） | 原槽位数、前驱 / 当前 / 后继责任和归档补送规则；这些是逻辑预算，不是 RSS 上限 |
| 原控制消息保留 | 按真实完整签名控制证据保留当前四槽和有界排空空间，不再用四个巨大数据正文占据控制预留 | 辅助流量不能抢控制槽，旧句柄不提前释放 |
| 原 state / packet owner | 最大声明键 32,768；按现有最大管理行 31 键 + 每批 42 键收费 | 捕获仍最多 65,536 树节点 / 16 MiB，单次 64 节点 I/O，候选 owner 256 MiB / 两批；不复制账户库 |
| 原负载驱动 | 一帧最多 1,024 行，持续补货至少一整帧 | 8,192 在途上限、256 高度有效窗口、四节点全部回执终点不变 |

状态测试覆盖 1,024 个独立付款 / 收款账户，声明 10,240 项、实际变更 6,144 项，完成原树捕获、错误父根拒绝、原持久化及余额 / nonce / 额度重读。进程负载仍用原夹具的 **16 付款方 + 共享收款方**；这不证明 1,024 个独立账户的进程创世已验收（当前初始化还有自己的 32 账户限制）。

8 MiB 预算下的 1,024 行准入已经成立，不代表所有 8 KiB 行组合、最大管理交易混合、全部资源高水位都已实际压满。本轮实际普通转账每行 5,448 字节。

## APFL 实际编码

真实 16 付款方负载每帧 1,024 行：

- 展开规范输入：5,578,752 字节。
- APFL 编码：3,438,064 字节；原 native application 对象：3,438,229 字节。
- 其中独立签名：3,388,416 字节。压缩没有省略任何签名。

结构往返测试另覆盖 1 / 16 / 1,024 公钥，APFL 分别为 3,399,992 / 3,438,064 / 5,437,808 字节，所有行逐字节还原。该结构测试使用模式签名，**不是密码学验签证据**；真实四进程负载才使用真实签名。

## 同条件性能

统一候选 AOEM、node / client、CPU 业务执行、24 workers、查询批 128。只在各组切换签名后端；GPU-required 不静默回 CPU。正式测量关闭诊断，未同时运行其他压测或重型构建。业务成功、费用、余额、nonce、授权预算、四节点回执和原库冷恢复均在各成功轮核对。

## 阶段诊断

另一次开启诊断的 4K CPU / GPU / CPU 结果约 2,762.73 / 402.96 / 2,194.19 TPS，仅用于定位，不混入正式性能组。

GPU 入口节点单次 `admission` 最长 **3,287.252 ms**，包括懒初始化 / 资格检查与实际验签，不能全称为 GPU kernel 时间。以入口首次验签完成为相对零点：另一个节点约 835.953 ms 已耐久签 nil，约 1,013.761 ms 才完成候选；到下一轮约 5,884.639 ms 才注册，约 5,903.209 ms 完成决定 ACK。记录显示首次准入长耗时、对象投递等待，以及先签 nil、候选随后完成、再等待下一轮的时间链；尚未分离各项因果贡献，没有修改原轮次超时。

四节点高度 1 最晚耐久 ACK → 高度 4 最晚 ACK 的后三高度区间分别为 **454.467 / 457.747 / 478.956 ms**。本样本稳态差别远小于全程 GPU 慢轮次；这是局部区间，不替换含首次等待的总 TPS，也不能代表 65K 全程。

`native_delivery.received` 包含对象完整重组与解码，不是纯网卡传输耗时；候选完成事件也包含候选持久化。现有记录不能精确拆出 KAT、GPU 初始化、所有网络字节 / 重传或每种等待。见 [阶段原始数据](4096-diagnostics-paired.json)。

## 验证与失败保留

初次大正文恢复在高度 40 回执观察时超时，尚未启动离线节点，**不是恢复通过**。该次逐笔查询 1,024 行；后来夹具改用已有 128 行批量查询，保留每行顺序 / 数量 / 全部终态 / 节点一致性，并对首尾做 v1 对照，保留重复 selector 和未知 hash 反例。90 秒共同期限及每请求 5 秒没有扩大。

改为批查询后的第二次仍有 QueryTimeout，见 [批查询失败](recovery-batch-query-failure.json)。因此不能把首失败归结为逐笔遍历；原日志也未区分单请求期限与总期限。见 [首失败报告](recovery-first-failure.json) 和 [首失败日志](large-process-recovery.log)。之后仅在原 helper 增补失败时 client / chunk / shared deadline / sent / 最长 poll / completion 数量，不增加重试。

相同生产程序开启原诊断后的第三次完成：离线 112.278 秒、健康三台推进 40 高度；第四台追赶到耐久高度 1 强杀，检查目标高度 40 归档确实不存在；原库重启、取得归档和精确正文、本地执行，随后收款账户再次消费。最终四台高度 41，1,064 笔回执 / 余额 / 授权 / nonce / 费用及冷恢复一致。四库高度 40 归档均含精确的 1,024 行，APFL 3,402,960 字节且 SHA 相同。见 [诊断恢复通过](recovery-diagnostics-pass.json)。**这证明该样本可恢复，不解释前两次查询超时，也不证明无诊断已稳定。**

补充最小失败上下文、修复测试 Clippy 后，最终关闭诊断的复验也通过：离线 **111.281 秒**，同样在高度 1 且高度 40 归档缺失时强杀；四节点最终高度 41，原库冷恢复和全部经济核对通过，整项 130.12 秒。见 [最终无诊断恢复](recovery-closeout-pass.json)。它没有触发新失败上下文，因而仍未解释前两次超时；不能签查询稳定性根因已修复。
