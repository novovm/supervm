## v1历史方案：排序现已撤回

1. 原 `consensus/native_lifecycle/ingress.rs`：
   在同一个既有两槽输入队列中，两项都是 Raw、同来源、同完整 scope（除 sequence）时，
   优先取已经完成接收的较早 preparation sequence。相同 sequence 保留 FIFO；
   不同会话/域/来源不互排，不等待缺失序号，不把 preparation sequence 当账户 nonce，
   不改 Checked 续传、准入、权限或最终发布。没有新增缓存、队列或线程。
   这是减少已到输入逆序准备的薄接线，不声称已消除上表全部入口排队。
2. 原 `service/rpc/gossip.rs`：
   `repair_recipients` 对选中行的现有 `gossip_missing` 取交集并与 `available` 相交，
   让一次原 fanout 同时服务所有确实遗漏整组的可用 peer；部分重叠、退休行和空集合不共享。
   仍由原 `try_submit_transactions_to` 重查每个 peer 的容量，只有实际 `reserved` 清位。
   anchor round-robin、fresh/repair 交替、单个 retained offer、消息/字节上限均保留。
   `repair_inputs_reserved` 计共享批唯一行数，不是 peer 副本数或实际线上字节。

候选测试源码包含原队列排序、域/来源隔离、空/退休/部分重叠反例，
以及真实签名资产准入和原 UDP 双 peer 槽释放的共享修复反例。
本轮实际验证记录如下，不把代码审查当运行验收。

## 综合结论与仍未完成项

**保留的代码收益：同一原NovoRUDP owner批量提交初发数据报，减少逐包系统发送；
同一repair正文共享给当前确实缺少全部所选行的peer，避免重复扫描共同缺失掩码。**
单包、repair、metered、deferred及共享socket仍按各自原合同推进，未靠扩大配额或TTL提速。
同字节本组约一成TPS及尾延迟改善已兑现；普通账户模型和12K性能恢复仍分别签收。

剩余位置有具体证据，但未完成整个12K差距的因果分解：

1. v3相同实现的诊断里入口NativeIo仍约4秒/16K，发送提交采样估算约1.46–1.48秒，
   独立AEAD封装约1.18–1.23秒。批发只摊薄提交成本，没有删除逐包密码学、接收或修补。
   这些是开启诊断的v3累计墙钟，不是v4正式轮CPU利用率或固定带宽极限。
2. 输入48对象完整初发保留，补片却增加；收齐P95仍约0.82–0.92秒，最大超过1秒。
   尚未把每个初发缺口进一步分成真实丢失、系统排队、处理反馈延迟。
   不能把所有补片说成重复，也不能把补片数换算物理丢包率。
3. CPU h6正文/耐久ACK等待确实缩短，但入口正文身份完成→候选完成仍约140–156ms，
   其中执行、状态/持久化边界尚未拆成完整因果；不拿该样本解释全部高度。
   SDK公共入口接收外部UdpSocket，可能已有OS共享句柄，未冒充专有socket开启全局分段。
4. v4正式轮仍有约13.3万–17.9万回执查询；这证明存在观察工作量，不证明查询是主因。
   本轮关闭诊断，没有重新测线上包/流量，不能把v3字节数直接套成v4正式轮实测。
