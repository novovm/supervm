# 原生投递流量账与重复数据收口

基线 `9cf5ac7091bcd59a0d4c4ecb76d6c5ec3a7198c9`，开发分支
`dev/mldsa65-identity-closure`。原链路仍为
`native_execution_tick → NativeChannel → NativeObjectLink → NativeUdpSession`。
不修改 ML-DSA、账户模型、费用、授权、nonce、共识票数、超时、发送配额或正式 AOEM 库。

## 已测的流量，而非逻辑入队计数

`NOVOVM_PROFILE_NATIVE_IO=1` 沿原诊断增加固定容量、线程本地计数，默认关闭。
成功发送计实际完整 secure datagram 字节；WouldBlock/额度不足只计尝试，不计成功。
初发、补片、probe 是成功写入后的分类，ACK/其他单列。接收区分通过认证后首次接纳、
重复分片、完成历史命中、背压及拒绝。不同阶段互相包含，不能相加。
UDP 字节不含 IP/UDP 头；不能由补片比例推导物理丢包率。

主机沿原投递句柄记录终结状态与实际写出，正文精确内容摘要只用于有界诊断，
不授予权限、不充当正文缓存。相同节点/peer/正文有多次尝试，不自动代表多次完整交付。
历史命中可能只需少量分片就完成；不同 peer 仍有独立投递责任。

16K 前样本见 [汇总](before16k.json)、[流量账](before16k-ledger.json)、
[未改写原报告](before16k.raw.zip)。四节点最终一致、原库冷恢复及经济核对通过。
诊断 TPS 2,355.78，P95/P99 3.609205/3.667515 秒，79 个高度。
该轮应用帧为128行，不能冒充64×1024的正式65K容量/性能口径。
快照包含节点启动和验后查询，旧客户端未记录其自身字节；它不是同步截取的整网交易窗口。

## 两处有依据的修改

1. `CandidateBodies::requests` 复用原 `retains_promoting_successor`。
   已持有精确正文、未退役且完整父状态已由journal ACK确认时，不再请求第二份。
   缺失、不同正文、错误父态、换轮、恢复条件仍不满足该持有判定；不绕过验签、执行或发布。
   修复前新增反例真实失败，见 `owned-body-before-corrected.log`。
   首次夹具构造失败日志 `owned-body-before.log` 单独保留，不作为旧缺陷证据。
   不删除 Decision DONE 后的自动正文续送，它仍承担现有归档恢复责任。
2. 原查询响应使用 `NVQUERY5` 紧凑编码，而非回传整个 Request。
   同一 typed Response、同一服务端待请求校验、同一客户端待请求、同一查询频率与最终性终点。
   域分离请求摘要承诺全部规范请求，会话、序号和逐行顺序仍验证；旧响应格式拒绝。
   128条未确认状态4,273→205字节，128条最大宽度最终状态9,439字节。
   16K计时内35,474次查询有4,540,672条回应，其中94.43%未最终确认；旧回应反复传回
   的128个哈希合计145,301,504字节。这是源代码与请求次数推算，不是已测节省量。

节点/SDK/CLI须统一升级未发布查询响应格式。旧节点配新客户端不得拿来作A/B，
不添加旧格式生产兼容或静默回退。查询可见性不是共识内部持久确认时间。

查询省包已兑现，但整链没有因此提速，正文发送量基本未变。
没有改查询频率；更快响应让原观察器完成更多轮查询，结果组成也改变。
不能把两轮全部流量差都精确归因于新编码，更不能用单个编码比值替代TPS。
正文持有者反例已修，不等于已经减少了所有归档续送或解释全部慢轮。

新客户端增加同一poll线程的计时前后累计快照（旧轮无该证据）。本轮客户端实际
写出498,845包/487,820,605字节：查询sealed 329,873,853字节；应用输入sealed
157,946,752字节，其中66,553,104字节补片。它仍不能直接解释成物理丢包，
也不能与节点生命周期快照拼成同一精确时间窗的整网丢包账。

其中查询初发264,264包，恰为44,044请求×6包，共290,513,846字节；响应虽然变小，
原请求仍完整发送128个哈希。查询占本轮客户端发包73.06%。返回的Finalized行从
252,976增加到1,418,018，包含已观察结果的再次查询，并非新增交易。
这揭示原观察器/请求端的重复工作，但本轮不改变轮询规则或四节点验收终点来制造提速。
正文初发减少6,090包、补片增加6,265包，不能将正文总量基本不变描述为正文提速。

## 65K与空间阻断

[持续65K失败记录](continuous65k-cpu-failed.json) 仍使用1024行/块、8MiB、8192在途、
原四节点全部回执终点，诊断关闭。运行中原节点1/2/3持久写入分别收到
`AOEM storage provider ... No space left on device ... RocksDB ... 000054.log`。
保留stderr、报告、原数据库和journal；未清库、未复用损坏签票域、未将部分交易折算成合格TPS。
本次运行的磁盘峰值被低估：历史结束后的单轮库约1.41GiB，不能作为运行时空间上限。
目前停止大负载；完整CPU/GPU同字节及持续65K复验仍受磁盘空间阻断。
这解释的是本次明确写盘失败，不解释历史约3K、CPU负向或此前查询超时。
