# 原Windows批发提交：五段联合计量

基线`dfbe1530`，继续原开发分支；本轮只加原发送函数计量，不改发送策略。
没有scatter/gather、并发、配额、socket选项策略、分片、nonce/AEAD、补片、账户或共识变更。

## 实现与五段边界

原`send_udp_segmented_batch`保持签名和错误合同，观测入口回到同一个`send_batch`
和平台函数，不是第二套发送实现。仅已有`NOVOVM_PROFILE_NATIVE_IO=1`时，原
`SegmentedUdpIo`提供一份栈上观测记录；关闭时不取Instant、不计数或录制样本。
原mutex、设置分段大小、`Vec::with_capacity`、逐wire拼接、`socket.send_to`和结果规则保持。

| 阶段 | 严格范围 | 不包含 |
| --- | --- | --- |
| lock_and_option | 原mutex取得/等待及必要的setsockopt | 其他持锁工作、释放锁 |
| allocation | 原Vec::with_capacity | 拼接、释放缓冲 |
| concat | 原extend_from_slice循环 | 分配前验证、系统发送 |
| send_to | 原socket.send_to实际调用 | 拼接和结果检查 |
| result_check | 原返回值检查、原错误/短写转换 | payload释放、诊断汇总 |

五段来自**同一批次**、互不重叠。每61个非空原UDP批次选择一次联合计时；
其他批次仍只计数。未采样或未进入的阶段是null，不用0冒充零耗时。
逐样本total从取得锁前到返回平台结果并释放临时资源后，止于计量汇总之前；
验证、部分记录开销、payload/锁释放等留作残差。begin前元数据/初始统计及finish汇总
不在该total内，但仍在原外层SocketBatchSend内，不能把两种total强行等同。
这些是同步调用墙钟，不是CPU时间，更不是纯内核CPU或真实网卡耗时。

## 计数、分位数与资源

每个打开诊断的批次统计请求datagram数/字节、分段变更尝试、Vec分配请求、
分配后及拼接后capacity、实际复制字节、send调用数、原始written字节、
完整接纳批次/行/字节、失败、设置失败、WouldBlock和短写。
`option_change_attempted`不是设置成功；原始written也不等于完整批次成功或peer已收到。
空输入在原carrier入口直接返回，不进入这个非空owner统计。

allocation_requests是原Vec源码分配请求次数，不是全局allocator或物理页分配事件。
capacity变化实际观察前后值，不硬填0；累计capacity字节不等于活跃内存峰值。
输入复制计量是拼接的实际payload.len，不包含内核复制、加密或其他owner。

原诊断owner保留最多1024份联合样本，快照时才排序、按nearest-rank计算P50/P95/P99。
累计计数/采样覆盖原进程启动至最终进度快照，可能包括启动及负载后处理；
最终快照在交易计时结束后取得，不属于主TPS时钟，不是按交易drive时窗裁剪的数据。
不在发送锁内排序、输出文件或逐包打日志。samples_seen/omitted_samples明确记录覆盖；
如回卷，分位数和sampled_ns只属于**保留的最后1024样本**，不是全部历史采样。
常规all-attempt计数与保留样本的时长不能混作同一个统计范围。

## 验证

[UDP原实现测试](udp-batch-tests.log)12项通过：真实Windows分段回环比较普通/观测入口，
逐字节检查完整数据报和短尾、恢复单发；同时检查采样/不采样、capacity及复制计数。
空批次/非法批次不分配、不复制或调用发送，观测记录不携带上一次结果。
结果分类确定性反例保留原WouldBlock和WriteZero语义：短写不得伪装成功前缀。
这些纯分类输入不是实际UDP短写或WouldBlock负载证据，不能冒充真实投递。

网络测试同时覆盖联合样本有界、未进入阶段null、错误/短写不计成功。
第一轮严格库Clippy发现本轮新增`% 61 == 0`触发is_multiple_of告警，
已按当前工具链修正，没有关闭告警，原日志保留于[首次失败](clippy-first-failed.log)。
它不是历史故障，不把后续通过补写成首次即通过。

## 决策

**这些同机回环窗口支持情况B：主要时间位于原send_to调用内，分配/拼接不是优先项。**
暂不改scatter/gather、缓冲复用或Frame，更不添加线程、扩大批次/配额来追数字。
下一项应审查原同步分段提交/回环交付工作，而不是继续重写Rust数据结构。

但send_to区间仍包含用户态Winsock、系统调用、内核交付及可能调度/等待，
不是新的纯内核CPU归因；不能据此断言网卡带宽饱和、真实多机相同比例，
也不能把88%当成整链88%可消除成本。未重录ETW，没有承诺这项研究能直接达到4K。

[网络回归](network-tests.log)924通过、13忽略，单测试线程；[库Clippy](clippy.log)、
[测试Clippy](test-clippy.log)与[node/client构建](build.log)通过，未移除检查。
**本轮是成本拆分，不是新性能优化；稳定4K未达到，12K未恢复。**
main、正式AOEM/随包库、Auto、部署、旧数据库及journal保持不动；不重做ETW或Frame专项。
