## 三边界与物理DR槽

PID14836/TID6612同一调用入口RSP=0xcdeeeee548，writer self=0xcdeeeee660。
P0的RDX、P1的R14、P2的R14/RDX均为0xcdeeeee58e，等于该次LowerHex两字节栈缓冲区预期地址。
三个逻辑断点本次仍依次复用物理DR0。修正后的控制器按实际启用地址匹配，接受3条事件并关联成1次完整调用，coverage_issues为空。

## 多线程核验的实际覆盖和缺口

启用请求后、首次继续前取得24个线程快照，DR7当前均为0。
P2后的禁用请求、再次继续前取得23个线程快照，其中22个DR7=1、1个DR7=0x401，DR0仍显示P2地址。
这些是CDB在停点上的寄存器快照，设置和禁用请求尚有待恢复运行时应用的可能。
因此ARMED和CLEARED只是采集阶段标签，不能直接宣称所有线程的硬件已经完成装入或清除。
实际P0/P1/P2命中记录证明TID6612当时存在对应启用执行槽，未扩展成其他线程全部经过目标路径的证明。
新线程事件过滤已设置，本次未取得CREATED记录。24到23的数量差不补成创建事件，新线程继承情况仍未验证。
后续解析器已支持DR0–DR3，旧三槽文本兼容重放使用DR3=0占位并显式标记，未冒充历史DR3实际命中值。
本轮清理时清除断点并detach，最终CDB和全部测试节点均结束，没有遗留测试进程。

## 采集组停滞原因及修正范围

我将多线程快照的~*e内联放入P2回调块，导致回调尾部的PTR_CHAIN_DONE及gc没有到达。
目标停止更新报告，控制器约53.4秒时触发report_stall_interference_gate并受控结束。
这项诊断命令错误导致采集组失去代表性，不能将该组低CPU和报告停滞归因NOVOVM业务行为。
三条实际寄存器记录在尾部错误前已完成，控制器本次也已接受全部三条。

已在既有PID43712转储中离线复现同一命令块的尾部缺失。
将多线程枚举放入独立命令文件后，同一离线检查可到达CALLBACK_TAIL_REACHED和OUTER_TAIL_REACHED。
修正保存在本机独立回调文件，原实际运行脚本、日志和哈希均保留。
该修正尚未重新运行验收，本轮没有再次启动节点，也没有追加正常调用次数。线程专用命令语法另按微软文档核对。[Microsoft线程控制说明](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/controlling-processes-and-threads)
