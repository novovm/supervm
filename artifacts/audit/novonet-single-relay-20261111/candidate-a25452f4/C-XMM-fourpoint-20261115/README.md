# 原 a254＋AOEM966 的四检查点隔离实测

## 结果

本轮实际运行三组原二进制对照，全部使用 LocalService、新隔离数据库及各组独立生成的测试密钥。使用原 NOVONET loopback 四进程通信、网络对象周转和周期 status 报告。原程序、AOEM 和精确 PDB 的哈希保存在 measurement-public.json。

修正后的四点组取得 34 次同线程、同父帧的完整调用，136 条检查点记录。四处的 XMM6/XMM7 原始 32 字节均等于该运行模块中的空表模板。本轮未观察到首次变化区间，原始故障仍未复现，Clone 恢复失败和 ABI 违规仍未证实。

原库、身份和历史转储保留。最终核对没有本轮残留节点或CDB进程。新测试任务已删除，专属 novovm-xmm4-a254.exe 的临时 WER 规则已清理，旧规则保留。WHEA 前后无新增 RecordId。

## 首次四点尝试的失败必须保留

第一轮四点组在46.951秒触发报告停滞守卫，所有隔离节点被控制器用0xE0000001终止，CDB退出0。它没有发生自然崩溃。

原CDB日志实际有一条检查点0命中，线程25836，停在原RVA 0x7721fb。控制器从控制台stdout管道没有接收到这条通知，故一直未发送继续命令。该失败证明了通知链路存在问题；它不能用于估计四个检查点正常运行时的性能损失。

修正仅将控制通知读取改为原CDB日志的增量字节游标，保留末尾不完整行。已有真实失败日志用于核对能识别该事件。随后只在全新目录重做四点组，前两组未重跑。失败日志、退出记录和新运行分别保留，未将其拼接为同次寄存器历史。

## 四个硬件检查点及线程覆盖

| 编号 | 原RVA | 观察时点 | 命中数 |
|---|---|---|---|
| 0 | 0x7721fb | 两份模板载入后 | 34 |
| 1 | 0x777bad | signature_work 发布后 | 34 |
| 2 | 0x777c36 | network_probe_observation 返回后 | 34 |
| 3 | 0x77823e | archive_work 写表前 | 34 |

使用CDB原生 ba e 1 配置四个执行地址，按该次实际模块基址处理ASLR。读取目标四处代码字节与原PE相同。四点组实际status线程为15188，目标PID35412。136次实际命中均核对调试器上下文的DR0-DR3为四个对应地址，DR7各槽启用且类型/长度位为执行断点。

初始附加停顿时，外部GetThreadContext读到各线程的DR为0，不能用这份外部初始读数证明执行期间覆盖。因此本次将覆盖结论限定在实际命中的status线程和本次窗口，并以每次事件的调试器DR状态、原RIP及全四点序列复核。其他线程未来是否会执行status，当前记录没有证明。硬件执行断点由调试寄存器控制，命中仍进入调试器。[Microsoft processor breakpoints](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/processor-breakpoints---ba-breakpoints-)

每次事件在目标停住时读取1232字节原AMD64 CONTEXT，先成功写入本机受保护目录，再发布选定标量。XMM6/XMM7直接取该结构的原始32字节并与目标内存常量逐字节比较。原始CONTEXT不进入Git。受保护目录中的136个文件没有由取证账户另行重开计算哈希，此项保留为复核限制。

公开事件按线程ID、调用序号、父帧RSP、返回地址及栈边界分组，34组均为0→1→2→3，没有未完成调用和检测到的缺点。调用序号可区分同一栈地址的后续复用。本轮34/34只覆盖有检查点0入口的调用；调试器在约15秒附加，附加前的调用没有记录。

## 三组实测干扰

每组剔除前25秒后保留30个目标报告间隔。以下分位数仅描述该短样本。

| 指标 | 无调试器 | 仅附加 | 四检查点 |
|---|---|---|---|
| 报告间隔P50，秒 | 5.034350 | 5.025073 | 5.113272 |
| 报告间隔P95，秒 | 5.051848 | 5.044208 | 5.158036 |
| 报告间隔P99，秒 | 5.067894 | 5.052501 | 5.166793 |
| ticks/秒 | 821.786 | 873.570 | 762.408 |
| reported_data_writes/秒 | 14.453 | 14.365 | 14.400 |
| 目标CPU秒/墙钟秒 | 0.037514 | 0.036111 | 0.043007 |
| 目标上下文切换/秒 | 725.448 | 736.931 | 829.871 |

四点组相对无调试器，报告间隔P50增加1.568%，ticks速率下降7.226%，网络写计数速率下降0.368%，目标CPU使用量增加14.643%，上下文切换速率增加14.394%。相对仅附加组，ticks速率下降约12.73%。固定顺序、独立新库以及短时负载波动会影响这些对比，当前不能将差异全部归因某个检查点。

这些CPU和上下文切换指标仅针对目标节点，未测量调试器/控制器的总CPU，也没有完整系统调度轨迹。资源计数采样不能替代线程调度时间线。

原二进制没有输出每次status完整调用耗时，故三组报告间隔不作为查询延迟。四点覆盖区间的34次观察跨度中位数85.296ms，最小47.722ms、最大126.618ms；该跨度包含原工作、调试器暂停及控制器响应，并且始于模板载入之后、终于archive写入之前，不能代表整次查询耗时。控制器响应时长字段在写出事件之后才赋值，最终公开事件没有持久化该字段，因此本轮没有可复核的逐回调响应耗时分布。

## 证据结论及下一步边界

本轮证明四检查点能够在原a254及真实隔离网络负载下取得同次向量记录，并取得短时干扰数据。136条记录未显示XMM变化，不能排除Clone或其他路径在原故障条件下仍有异常。

当前没有首次变化区间，也没有首次异常指令。没有生产修复。三分钟观测没有覆盖历史自然故障时长，无法据此认定长期采集低干扰或C节点已经修好。原始包序、历史并发条件、失败调用中恢复槽内容仍然缺失。

这一轮到三组测量及失败保全为止，未自动进入66分钟长跑。原库身份及失败现场继续保留，双中继暂停。诊断脚本和原始日志位于本机ignored target，公开Git仅保存脱敏事件、调用关联、度量与结论。
