## 结论：保留和入口接入成立，时序资格拒绝

按预设“各轮分位数的中位数比值”计算：查询 P50 **+56.4%**，P95/P99
**+24.9%**，poll P95 +5.3%，循环速率约-0.006%。因此拒绝本版本长期复现；
不继续以更大缓冲区、更多正常查询或放宽门槛来制造通过。

| 短时组 | 查询样本 | P50 ms | P95/P99 ms | 平均占用CPU核 |
|---|---:|---:|---:|---:|
| baseline 0 | 16 | 6.5650 | 16.5543 | 0.0653 |
| instrumented 1 | 16 | 8.4723 | 18.7426 | 0.0628 |
| instrumented 2 | 16 | 13.0488 | 21.6757 | 0.0655 |

每组仅16个查询，P95/P99在此样本量下均为最大值，**不是可靠尾延迟估计**。
两轮采集版也有明显波动，不将56.4%解释成稳定性能常数或单个hook的因果开销。
基线单节点峰值RSS约86.2–86.8MiB，采集版约90.2–90.6MiB；循环速率受1ms休眠
和固定探测计划约束，不是网络容量/TPS。上下文切换和系统CPU原数见JSON。

采集版两组共保留8,387组完整源码边界（50,322条），接收对象和pad→writer文本
指针/长度对应，无已观察错位。A保留1,992对创建/Drop，A/B均无覆盖、重入失败或
已观察未登记损失。另有**2,137,981个目标调用组被明确采样省略**，不能称全历史。
各通道没有被普通格式化事件互相挤出；这只证明本次窗口的保留，不等于全进程
所有对象/引用计数和生命周期覆盖。

16个目标进程与调试器均退出0，无本轮异常转储；各组sender Object DONE均32，
接收完整性分别29/30/29/29，时间资格拒绝3/2/3/3保留，未绕过认证。
Carrier活动/持续2048记录淘汰/原失败输入序列仍未覆盖。
**首次错位未定位、原始崩溃未解决、生产代码未修复。**

本轮有效结论是：编译期实际入口钩子能补源码参数关联，但当前逐调用回调/比较与
标准库重建组合不能满足本轮时序要求，不能作为长时原故障捕获器。若后续继续，
应先缩小到“异常条件才导出”的调用边界检查，单独核验没有丢掉欲检测的不变量，
并重新测量；它仍无法提供历史原EXE尾跳寄存器。原二进制的同次失败完整上下文
仍是独立缺口，不以继续增加正常样例替代。本轮没有启动该后续实验。

## 四通道与保留范围

| 通道 | 容量（160字节/条） | 策略 |
|---|---:|---|
| A 网络对象生命周期 | 4,096 | 仅自身回绕；generation 关联创建/销毁 |
| B Writer 调用边界 | 8,192 | 以完整调用组采样 1/256；自身回绕 |
| C 网络/查询上下文 | 8,192 | 独立回绕，查询序号与对象摘要 |
| D 普通格式化 | 1,024 | 如收到10/11事件则计数并丢弃；本次产品导出不启用旧10/11钩子 |

每线程预分配约3.28 MiB；每通道分别记录写入、覆盖、主动采样/丢弃、重入失败及
未登记线程失败。预热后不在 record 路径分配、格式化或写文件；使用 TLS RefCell，
不新增互斥锁，但这不代表零同步成本或低干扰。正常结束才导出。

定向反例包含：20万条普通事件不挤占 A/B、B 自身超容量不影响 A、四通道未登记
丢失计数、截断文件拒绝。测试字段明确为记录器校验输入，不能当作真实对象履约。
实际网络组的D写入/丢弃均0，表示没有启用普通事件钩子，不表示未执行格式化。

生命周期覆盖仍有限：复用上一轮原网络准备/Drop/接收完成钩子，没有声称所有 Arc
计数变化、线程迁移、String 释放及 allocator 地址复用都被追踪。覆盖与对象缺口
必须看结果，不能因四个缓冲区存在就认定完整生命周期通过。

## Writer 入口到底记录到哪里

复制本机 Rust 1.94.0 rust-src，仅在该副本增加以下事件：

1. alloc `format_inner` 创建局部 String 后（101）；
2. core `fmt::write` 接收 output 后（102）；
3. `pad_integral` 的三个 `self.buf.write_str(buf)` 调用点之前（103）；
4. 原 `impl fmt::Write for String::write_str` 入口、读取 String 字段前（104）；
5. 同一实现读取 buf/len/cap 后、push_str 前（105）；
6. `format_inner` 返回 String 前（106）。

没有换成代理 Writer。只在原 profile 字节十六进制格式化的目标作用域启用关联；
周期查询以外关闭该作用域。每组带 OS TID、查询号、调用序号/代次及对象地址；
未采样组计数，入口接收对象仍在线比较，不一致时记录异常边界。
**未采样调用即使在线比较相等，也没有完整历史，不能当作已保留的失败证据。**

为了避免依赖 cdylib 引用 EXE 符号的链接失败，标准库副本使用一次性回调槽；
只有诊断 EXE 注册回调，其他 image 保持未登记。这不是生产 FFI 改动。

例如诊断 Writer RVA `0x37980`：`RCX/RDX/R8` 保存至 `RSI/RBX/RDI`，
`0x379cd call rax` 记录104，随后才在 `0x379cf` 读取 String 字段；105之后进入
复制路径。完整机器码和其他优化副本在 writer-code-public.json。

**证据等级限制：**这是插桩标准库的源码入口及静态机器码映射，不是原875/a254
EXE入口历史。插桩改变了序言、寄存器保持、函数布局和调用次数；没有记录原尾跳前
RSP/寄存器/栈槽，也未在动态记录中区分全部 LLVM 优化副本。不能用这些正常记录
反推 PID3228/37796 的首次错误指令。

## 对照方法

沿用已审阅的原 Driver、NativeLifecycle、NovoRUDP 和状态查询组合，仅在新目录
生成隔离身份/数据库。AOEM固定966；四进程回环，周期查询10秒，每组45秒，ABBA。
不操作外部 A/B/C/D 节点，不进行真实双中继。CDB使用 `-hd`，只处理异常/退出，
不使用逐调用断点、TTD 或 PageHeap。

对照版使用正常标准库，采集版使用复制并插桩重建的标准库。因此数字是**整套诊断
配置的差异**，不能全归因于事件写入。两版都使用同一历史源码、优化、Rust版本和
AOEM，但标准库构建/布局差异明确存在。各两轮的小样本不能证明调度等价。

预先设置拒绝线：查询 P50/P95/P99 或 poll P95 任一增加至少10%，循环吞吐下降
至少10%，目标退出失败、真实探测证据缺失、B入口缺失或 A/B 历史损失，均拒绝。
进程 CPU/RSS/上下文切换与查询间隔另行记录；未测量锁等待时长或逐次调度。
不以“没有动态分配”或“没有崩溃”替代门禁。

全内存异常转储仅在本地。当前正常结束解码器没有提供经验证的异常时原子导出；
异常时每通道最后一个槽必须视为不完整。没有异常发生就没有同次失败历史。
原输入顺序、多小时调度、生产进度文件发布和活跃 Carrier 未恢复，不能宣称原故障
条件已经完整复现。短时对照只评价新增采集方法，不以正常次数作为修复证据。

外部符号版本的标准库缓存；实际失败退出101及空启动日志保留在本地并列入清单。

原始 DMP/PDB、原库、身份和旧失败继续保留。首次破坏指令未找到之前，不提交
猜测性生产修复，也不恢复双中继。
