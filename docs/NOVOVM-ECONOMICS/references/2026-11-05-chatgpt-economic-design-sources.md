````markdown
### 为什么这样调整，而不是照搬旧比例？

你的原候选是：

**建设3,500万＋研发国库2,000万＋团队2,000万＋销售1,000万＋流动性1,000万＋推广500万。**

我建议的调整有四个理由：

**第一，把原来的“团队2,000万”拆清为创始人1,500万、团队贡献500万。**  
这与“创始人收益来自自己的创世持有和实际出售，不从订阅抽成”的既定方向一致。创始人首期50万可用，是给个人经济留一点实际空间，但并不保证能卖出或获得多少现金；剩余绝大部分保持长期释放。个人持有与项目国库不能混账。

**第二，把销售额度提高到2,000万，保留你此前提出过的发行销售规模，但不预先送给某家交易所。**  
这是销售库存上限，不是已经完成承销，不是上市首日全部流通，更不是已经筹到资金。具体渠道仍可变，资产归属和用途不能提前含糊处理。

**第三，将流动性NOV储备从1,000万降到500万。**  
我的理由不是“500万一定最优”，而是目前没有配对资产规模的证据。没有外部配对资金，单独放更多NOV并不会自动形成有效交易深度。你已有双轨清算规则明确：客户外部资产的托管储备不能拿来做市，流动性资产也不能算成自由国库现金。

**第四，将网络建设额度从3,500万调整为3,000万，但保留八年采购预算框架。**  
这笔钱应该帮助网络从启动补助逐渐转向真实服务收入，而不是永久按在线人数发工资。你的原文已经明确：在线、自报容量、重复回执、自造订单都不能自动取得公共补助。

**这里有一个科学上必须保留的限制：3,000万NOV够不够支持八年，不能只看币的数量。**它取决于实际服务报价、需求、可购买容量和收入。因此，八年是预算规划，不是八年购买力保证。

## 四、资产恢复：本轮建议不加额外恢复权，不能伪装成“没有风险”

我建议矩阵第5项填写：

原因是你当前已经在收口账户、用途密钥和权限边界，不宜为了“万一丢钥”再引入一条权限更大的恢复通道。**恢复自己的密钥，与由某个管理员重置别人的资产控制权，不是同一件事。**密钥管理本身也需要分别考虑保护、备份、丢失和泄露后的处理，而不是简单加一个“找回”按钮。[NIST计算机安全资源中心](https://csrc.nist.gov/pubs/sp/800/57/pt1/r5/final?utm_source=chatgpt.com)

**“3/5＋创始人必要同意”并不能容忍创始人必要同意钥永久丢失。**即使其他四人都在线，也不能擅自绕过它。这会阻塞新的相关国库决策，不能宣称没有单点风险。

因此，演练可以先选择“不设额外恢复”；正式长期资金安排中，需要你明确接受这种风险，或者另行批准**由原权利人事先授权、仅作用于指定账户／角色的继任机制**。不能现在以“恢复”为名，偷偷取消已定的创始人必要同意，也不能扩大成普通账户恢复权。

## 五、原生交易费：给出具体演练值，但不冒充正式最优价

### 建议演练值

**标准原生单签转账：0.00001 NOV／笔＝10,000最小单位。**

这里只针对当前标准Transfer及其既有资源边界。它可以作为该标准交易的固定报价，**不代表所有复杂执行、存储、证明都收同样的费用**。

### 成功、失败和重试应这样区分

| 情况 | 建议收费 |
|---|---|
| 授权有效、进入执行并最终成功 | 收0.00001 NOV |
| 授权有效、进入执行，最终形成协议定义的业务失败结果 | 收0.00001 NOV基础费；业务金额不转移 |
| 签名错误、格式错误、权限不足，或在准入阶段被拒绝 | 不从被声称的账户扣费 |
| 同一交易重传、重复查询、重复回执 | 不重复收费 |
| 节点断开、响应超时、尚无最终结果 | 先查询原交易；不能因为客户端看到超时就重新扣费或自动退款 |

“进入执行后失败仍付基础成本”是一个可采用的设计方向，其他链也存在失败仍收费的做法；**这里仅参考其成本原则，不照搬它们的费率、销毁或分配规则。**[Solana](https://solana.com/docs/core/fees/fee-structure?utm_source=chatgpt.com)

关键是：**收费依据应是授权和最终账本结果，不是某台节点单方面说自己干了活。**哪些错误属于准入拒绝、哪些属于已执行业务失败，要由统一协议定义；费用、去重与相关状态要在同一原子提交里处理。

此外，最低手续费不能单独解决攻击。原有资源上限和有界准入仍须保留，不能把“交手续费”变成无限消耗节点资源的许可证。

### 为什么暂定0.00001，而不直接宣布主网就收这个数？

这是一个便于验证小额扣费、整数守恒和分账的**演练参数**。真正的主网费率应结合成本测量校准，例如：

\[
\text{每笔费率（NOV）}
=
\frac{\text{所需资源与安全成本预算}}
{\text{预计有效交易笔数}\times\text{经批准的NOV参考价格}}
\times\text{准备系数}
\]

这个公式只是预算模型，参考价格不能由单一可操控的即时市场价格决定，也不能追溯修改用户已经签署的最高费用；你的双轨价格文档已明确区分市场价、协议清算价和服务报价。

给你一个不涉及币价假设的量级检查：

| 纯算术情景：持续12,000笔／秒 | 每日手续费总量 |
|---|---:|
| 每笔0.000001 NOV | 1,036.8 NOV |
| **每笔0.00001 NOV** | **10,368 NOV** |
| 每笔0.0001 NOV | 103,680 NOV |

这是按费率直接计算，**不是对12K性能或实际需求的预测**。这些NOV只是转移和循环，不因收费减少总供应。

## 六、手续费去向：建议90/10，但与订阅彻底分账

建议第7项填写：

> **90%归该类交易的合格执行、验证、必要传播和确认服务责任预算；10%归公共安全与运行准备金。没有创始人专属抽成，没有销毁。**

这一比例是我的新增建议，理由是：原生交易费首先应支付完成交易的实际服务，少量留作共同运行保障；研发与运营已经有创世国库，并有订阅20%网络用途，不宜对每笔交易再设置过重的项目抽取。
````

````markdown
## 一、UCA注册：应该对“占用公共资源”收费，而不是对“生成身份”收费

### 1. 先区分三个不同动作

**本地生成密钥和身份材料，不应收费。**这一步没有要求其他人长期保存你的记录，也不应该需要某个机构批准。

**把身份、控制关系或必要绑定登记到共享状态，需要承担资源成本。**这是大家要保存、验证和同步的数据，不能无限免费写入。

**申请好记名称、公开目录曝光或额外资料存储，是另一项可选服务。**不能把这些商业服务当成拥有基本身份的前提。

这属于我对原体系的细化建议，**目前读到的经济规格没有给出已经批准的UCA注册单价，也没有明确冻结注册保证金规则**。不能把建议写成已经存在的生产能力。

### 2. 建议的注册成本结构

我建议这样拆：

\[
\boxed{
注册支出
=
一次性登记执行费
+
必要的状态保存费用
+
可选的状态占用保证金
}
\]

三项性质不同：

**登记执行费**支付认证、校验、写入和确认等已经完成的工作，通常不退。

**状态保存费用**对应实际保存责任。最低身份记录、附加属性、可变目录记录，不能默认都承诺永久无限保存。

**状态占用保证金**只是限制同时占用大量状态的资金，不是服务者收入。只有在协议允许安全释放相应状态、没有未决义务时，才可能退回。**不能把这笔钱同时算成国库收入并拿去支付节点。**

作为外部设计参考，Solana把账户所需最低余额设计成与数据大小相关的可退存储保证金；这说明“执行费”和“占用状态的资金”可以分开，但不意味着NOVOVM必须照搬其参数。[Solana](https://solana.com/docs/core/accounts/account-structure?utm_source=chatgpt.com)

### 3. 收多少才合理？

**不建议现在直接定“注册费0.1 NOV”或“1 NOV”。**缺少两个关键数据：一条正式UCA记录最终需要保存多少字节，以及这笔费用究竟购买多久、多少副本的保存责任。

建议先按以下方法定价：

\[
F_{\mathrm{登记}}
=
P_{\mathrm{认证}}\times认证单位
+
P_{\mathrm{执行}}\times登记工作量
+
P_{\mathrm{写入}}\times新增状态字节
+
确认成本
\]

其中单价和计量规则应当是明确版本的公共规则，不能由接收请求的节点临时随意开价。

**相同认证方式、相同记录规模的UCA登记，可以显示为统一固定报价；底层仍要知道这个报价由哪些成本组成。**

若要先做价格敏感性分析，可以把**等值0.01、0.05、0.10美元**作为三档假设，测用户负担和批量注册成本；**这些不是正式推荐费率，更不代表运行时必须查美元价格。**

### 4. 注册收费不能证明“一人一个UCA”

收费最多提高批量注册成本，不能保证独立自然人数量。例如，纯算术上，假设每次不可退成本为0.01美元，1万美元仍可支付100万次登记。

而且还要看**攻击者的净成本**：如果攻击者控制提供服务的节点、能收回部分注册费，那么名义收费不等于实际攻击成本。

因此我建议同时保持：

**登记需要真实资金；记录大小和请求速率有界；多个UCA不能自动带来多份空投、免费月、节点补助或共识权重。**你现有文档已经明确“UCA唯一不等于自然人唯一”，公共补助不能只凭新增账户发放。

还有一个重要边界：**不能因用户没续费，就改变其资产归属、删除必要的控制证明或让别人接管UCA。**可到期的是附加服务，不是资产所有权。

对没有NOV的新贡献者，可以由已有明确预算的任务方赞助必要登记和结算费用；但应当有上限、明确出资人和实际任务，不能变成每生成一个身份就自动领取资金。这样才能兼顾你原来确定的“不要求先购买NOV才能提供资源”。

## 二、转账叫什么、怎样科学收费？

### 1. 名称已经确定：Execution Fee，执行费

你们货币架构已明确：

> 原生费用使用 **Execution Fee**；EVM兼容接口可以保留`gas_*`字段，但Gas不作为NOV原生经济的主要表述。

因此不需要重新起一个代币名称，也不用创造“燃料币”。普通界面显示“转账手续费”，展开后显示“执行费明细”即可。

顺便纠正一个概念：以太坊的Gas首先是衡量执行资源的单位，真正支付的是ETH。NOVOVM同样需要资源计量，只是不必照搬EVM操作码及Gas表。[ethereum.org](https://ethereum.org/developers/docs/gas/?utm_source=chatgpt.com)

### 2. 不按转账金额比例收，应按资源收

在其他条件相同的情况下，转10 NOV与转10万NOV，不应仅因金额不同就产生不同的计算费。

但以下情况可以有成本差别：新增收款账户、多签验证、更多状态读写、更大的交易数据、复杂执行或必须生成证明。

我建议原生计量模型采用：

\[
\boxed{
F_{\mathrm{执行}}
=
F_{\mathrm{认证}}
+
P_C C
+
P_R R
+
P_W W
+
P_B B
+
P_Z Z
+
F_{\mathrm{确认}}
}
\]

这里：

| 项目 | 应计量什么 |
|---|---|
| 认证 | 按算法、数量和协议定义的验证工作 |
| \(C\)：计算 | 确定性的指令、算子或标准执行单位 |
| \(R/W\)：状态访问 | 约定的读取、写入和新增持久状态 |
| \(B\)：数据 | 规范化交易数据及约定的传播成本 |
| \(Z\)：证明 | 实际要求的证明生成／验证，允许批量分摊 |
| 确认 | 完成该类交易所必需的确认工作 |

这与原文的“计算＋存储＋带宽＋证明＋路由”方向一致。**这是建议的计量表达，不代表上述分项已经全部在当前主链上接通。**

### 3. 不能按节点自报“CPU跑了多少毫秒”直接扣费

这是异构个人设备网络里尤其重要的一点。

同一笔交易，快电脑可能执行得快，慢电脑执行得慢。**不能因为分配到慢电脑，用户就被多扣十倍费用；也不能允许节点故意拖慢来增加收入。**

我的建议是：

**链上统一操作采用确定性资源单位和同版本计价规则；开放计算服务采用用户事先接受的报价和可验证交付条件。**

真实CPU时间、电费、设备折旧和带宽费用，用来**标定单价与判断经营是否赚钱**，而不是让各节点随意决定链上最终扣款。

同样，不能把所有重复验证副本的自报工作量无上限累加。协议需要多少复制和验证，应当事先有边界；节点自行多复制一百遍，不能让用户多付一百遍。

### 4. 失败、重传与批处理必须分清

我的建议是：准入前无效请求不从被冒用账户扣款；合法请求进入执行后发生业务失败，按协议结算已消耗的有界资源；未用预留释放；重复提交、网络重传和回执丢失不重复收费。

**客户端超时不等于交易失败，更不等于可以重新扣一次钱。**费用必须与原交易最终结果、去重和状态提交绑定。

批量优化也应反映到成本里。APFL或ZK把共享准备工作摊薄后，可以按明确规则分摊；**不能每笔都收一整份批量证明成本，同时又收整批证明费。**

标准单签转账可以最终呈现为一个很小的固定报价，但它应由这些成本算出来。**所以，上一轮的0.00001 NOV暂时不是科学标定后的正式结论。**

## 三、聊天流量：用户按订阅购买，节点按实际服务结算

这部分你的规则已经比较清楚，**不应该再改回逐条聊天向钱包扣币**。

当前确认的模式是：用户一次购买当月订阅；包含的用量不重复扣钱包；主国库通讯结算池根据真实合格服务日结。收入整体分为80%节点服务责任预算、20%网络用途、0%创始人个人订阅分成。

### 用户看到的是套餐，后台算的是资源

后台可以按下面的量计费：

\[
C_{\mathrm{聊天}}
=
P_B\times合格传输字节
+
P_S\times合格保管字节秒
+
明确购买的计算／容量成本
+
批量结算成本分摊
\]

原契约已经列出这些边界：

| 服务 | 计量方式 | 不应另外收费的部分 |
|---|---|---|
| 文本、图片、文件中继 | 合格有效字节 | 普通重传、环路、重复回执 |
| 离线临时寄存 | 字节×实际履约时间×批准副本 | 确认删除或到期后继续计时 |
| 语音视频中继 | 实际中继流量；约定的计算或容量 | 没有发生的转码、没有第三方中继的流量 |
| 目录、通知、握手等 | 纳入有界服务报价 | 按心跳、空查询次数“挖矿” |

这些是已有计费契约，不是新增一套收费架构。

**计量字节还要固定在哪一层。**按应用有效数据计，还是按特定密文封装后数据计，报价必须写明；不能应用层收费一次、同一段数据在网络层再收一次。

### 多副本和多跳，不是一回事

例如，购买**1 GiB密文、3份独立副本、保存24小时**，保管工作量是：

\[
1\times3\times24=72\ \mathrm{GiB\cdot小时}
\]

这是购买三份实际保管责任，不是重复收费。

但消息为了路由绕了几圈、节点重复发了几次，不应自动扩大账单。隐私路径的必要服务成本应事先进入报价和预算，不能因为预算紧张就静默降低隐私。

### 谁付钱？

建议继续沿原规则：**发送方已授权的预算覆盖一次投递、约定保管、领取与必要回执。陌生人给你发消息，不能自动扣你的钱包。**接收者自己另行购买的附加服务，才使用自己的预算。

用户购买套餐后，后台支付的仍是真实NOV。免费体验则由推广资金承担，不是节点被要求免费工作，也不是凭使用量增发。

**80%的责任预算不等于每天必须全部发完。**没有履约就没有对应报酬；尚未完成的保管和应付仍须留钱，不能把余额直接当利润分掉。

另外，聊天历史继续遵守你原来的本地保存边界，不能为了给节点创造存储收入，就自动上传用户历史、联系人和附件。

## 四、Web与内容分发：主要应该向购买托管和分发的人收费

你之前的Web Capsule设想已经包含：通过注册信息找到内容哈希或状态根，由节点提供内容，浏览器校验并重组；家用电脑可以提供存储、CDN和中继服务。**这属于已有设计方向，不能当作目前整套产品已经交付。**统一账户入口优化

### 1. 发布一个网站，不应只收一次“上链费”就承诺永久运行

我建议拆成四项：

**发布登记费**：登记发布者、版本、内容承诺、权限和必要入口。

**存储费**：实际数据规模、期限、冗余和可用性要求。

**分发费**：实际向访问者交付的数据。

**动态计算费**：搜索、查询、业务逻辑、图像处理等真正发生的计算。

一个普通静态网页，不应该因为被打开一次，就强制触发一笔全网共识交易。它可以通过已购买的分发预算完成交付，再批量结算节点。

### 2. 默认由网站发布者承担基础托管和访客分发

建议产品上采用：

> **发布者充值NOV并设置预算 → 用户正常访问 → 合格存储和分发节点取得报酬。**

访问者不必每打开一个网页都弹钱包确认。收费内容、付费应用或访客自购加速服务，可以另行约定，但不能“点击页面即暗扣钱包”。

同时，发布者的预算也必须有上限和反滥用规则，防止机器人刷访问把余额耗尽。**一条有效交付凭证不自动证明这次访问值得公共补贴。**

### 3. 用一个例子看清账单

假设某网站：

- 静态内容2 GiB；
- 保存3份副本；
- 服务30天；
- 发生10,000次实际交付，每次20 MiB。

则：

\[
存储用量=2\times3\times30\times24
=4,320\ \mathrm{GiB\cdot小时}
\]

\[
分发用量=10,000\times20/1024
=195.3125\ \mathrm{GiB}
\]

网站账单就是这些用量乘以已经接受的报价，再加实际动态计算与约定的结算成本。**浏览器已有缓存、没有再次发生网络交付的部分，不应伪造一次新的完整下载。**

### 4. 内容哈希上链，不等于内容永远可用

把哈希写进链，只能帮助识别和校验内容；还需要有人持有数据、持续提供读取。这一区分在IPFS的持久化文档里也很明确：缓存与内容寻址本身不保证永久保存，需要明确的保管安排。[docs.ipfs.tech](https://docs.ipfs.tech/concepts/persistence/)

因此，我建议：

**链上保存必要的身份、版本、承诺、权限和结算状态；大体积网页、视频、安装包由NOVONET存储与分发。**

发布者应付的“内容作者收入”也必须与“节点资源费”区分。卖一部视频所得的款项，不应全部被当作带宽收入。

另外，**聊天订阅的80/20目前不能自动套到Web托管、内容销售和任意应用收入。**这些服务可以复用计量结算机制，但分配合同要分别明确。

## 五、NOVOVM还存在合约吗？存在可编程业务，但不必被EVM合约形式限制

**不应该把“使用AOEM、执行与证明分离”理解成“没有智能合约了”。**

你的README明确采用统一Execution API，开发者声明函数、交易或任务及其安全要求；设计方向是WASM-first、多语言、可验证执行。也就是说，NOVOVM可以提供比传统EVM合约更广的可编程执行形式。

但需要区分三种东西：

| 对象 | 是什么 | 收什么费 |
|---|---|---|
| **内容／软件包** | 网页、视频、安装包、代码文件 | 发布登记、存储、下载分发 |
| **远程计算服务** | 在别人的设备上执行函数、任务或应用后端 | 计算、输入输出、必要证明与存储 |
| **改变共享资产或状态的程序** | 受授权和共识规则约束的业务逻辑，即合约意义上的可编程规则 | 执行、状态读写、证明及最终确认 |

**把一份软件上传到网络，不会自动让它成为安全的链上合约。**要改变余额或共享状态，程序必须进入受限、可验证的执行环境，明确输入、权限、版本、状态和资源上限，不能任意读取节点私有文件、使用不受约束的外部输入或支出用户资产。

### 建议把费用分为“发布”和“调用”

\[
F_{\mathrm{发布}}
=
登记验证
+
代码及初始状态保存
+
必要的确认成本
\]

\[
F_{\mathrm{调用}}
=
执行工作量
+
状态访问
+
必要的数据传输
+
所需证明
+
确认成本
\]

代码保存期间的持续成本需要单独覆盖，不能每次调用都假装重新部署；同样，一次发布费不能无限覆盖未来所有调用。

开发者可以赞助调用费，让用户无感使用，但必须限定应用、操作、金额和有效期，不能给聊天或网页进程无限资产支出权。

### ZK在这里怎样收费？

**需要证明的计算，应支付实际证明工作；能够批量证明的，按批次合理分摊。**不应每条消息都生成证明，也不能未生成证明却收取证明费。

还要注意：证明“程序算对了”，不自动证明“文件保存了一个月”或“流量来自真实客户”。存储持续性需要对应的验证机制，Filecoin使用时空证明检查持续保管，就是不同证明关系的一个外部例子；不能拿一个通用ZK标签覆盖所有履约。[docs.filecoin.io](https://docs.filecoin.io/storage-providers/filecoin-economics/storage-proving)

**当前实现边界仍须保留。**本次读取的原生Transfer解码入口明确拒绝Execute／Governance，因此已有转账闭环和TPS，不是任意原生应用或合约调用已经完成验收的证明；这也不等于仓库里的独立EVM兼容能力不存在。

## 六、小用户怎样靠提供服务赚钱？关键不是手续费高，而是有真实订单和正毛利

**我建议把小节点的主要收入放在它们适合提供的存储、缓存、内容分发、合格中继和小型计算任务上，而不是期望每个小节点都分到全网转账手续费。**

这与你原来“不同职责、真实劳动产生收入”的设计一致。原经济文档也明确，只有实际服务、事先购买的可验证容量或有预算公共任务才产生报酬；不能靠在线、设备数量或自报占用发钱。

### 节点经营必须算净利润

\[
\boxed{
净利润
=
已结算服务收入
-
增量电费
-
带宽成本
-
设备折旧
-
存储与维护成本
-
约定由节点承担的其他费用
}
\]

你原文曾使用“提供者净收0.08美元／GiB、成本0.05美元／GiB”作假设测算，**不是市场报价或已批准费率**。沿这个例子，再假设每月固定成本30美元：

| 每月实际付费服务量 | 收入 | 变动成本＋固定成本 | 净利润 |
|---|---:|---:|---:|
| 1,000 GiB | 80美元 | 50＋30美元 | **0美元** |
| 5,000 GiB | 400美元 | 250＋30美元 | **120美元** |
| 11,000 GiB | 880美元 | 550＋30美元 | **300美元** |

第三行若均匀分布在30天、每GiB服务对应一GiB有效出站，平均约36.5 Mbps，尚未算峰值、协议开销、离线和其他业务。

**所以“有50 Mbps上传”不等于“能月赚300美元”。还需要足够的真实订单、合格交付、可用时段以及可成交的收入。**

### 对小节点最有帮助的产品设计

我建议重点做三件事：

**让任务适合普通设备。**缓存热点内容、存储部分分片、承担有预算的小任务，不要求每台电脑保存全网数据或生成最重的证明。

**让收入和成本看得见。**展示真正到账、待结算、预计成本和资源预算；高峰时用户可以减少共享，不把自己的日常使用拖垮。

**让结算足够便宜。**累计微额、批量日结，避免赚0.001 NOV却为了领取花掉0.002 NOV；不足最小结算批量的收入继续保留，不能清零。

早期订单不足，可以用创世建设预算购买真实备用容量和公共测试，但那是有限采购，不是永久收益保证。服务需求没有增长时，不能靠增加UCA、相互刷单或提高账面NOV奖励制造繁荣。

还有一点：**NOV到账是代币收入，不等于固定美元现金收入。**节点能用它消费服务；能否按某个价格出售，还取决于真实市场，不能承诺固定兑付。

## 七、现在最应该冻结的不是五个价格，而是同一笔钱只花一次的规则

建议所有业务共用以下处理顺序：

**明确资源与报价 → 用户或赞助者授权上限 → 真实资金预留 → 合格履约 → 去重核销 → 指定服务者到账。**

对每项费用，都明确：

**付款方、购买内容、计量单位、最高费用、有效期、履约证据、失败／退款规则、最终收款方。**

尤其要禁止这几种重复：

- 用户买了聊天套餐，再对套餐内每条消息扣钱包。
- 订阅收入先分80/20，节点日结时又把同一笔收入重新分一次。
- 已支付一次文件交付，再对普通重传、领取和必要回执完整收费。
- 批量证明已收一次费用，又对每笔交易各收一次完整证明费。
- 保证金既作为用户可退余额，又当作国库可用收入。

这些预算、去重和“同一资金只分一次”的原则，在你的原计费契约中已经存在，应当补齐具体业务对应关系，而不是重造结算系统。

**我的最终建议是：UCA对公共登记资源收费，转账按Execution Fee收费，聊天沿订阅与日结，Web按托管／分发／计算收费，合约或应用按发布与调用收费。小节点凭真实服务赚钱，而不是凭账号数量或设备在线领钱。**

**下一步定价的依据，应当是一张覆盖“登记、转账、寄存投递、内容分发、程序执行”的实际资源成本表。没有这张表之前，不冻结统一每笔费率，也不把上一轮90/10建议推广到所有业务。**
````

## S3 按额收费纠偏、成本与定价公式

````markdown
King，**可以按转账金额收费，并不存在“区块链技术上不允许按比例收费”的限制。我上一轮把“资源成本不随金额同比增长”说成了“不应按金额收费”，确实过于绝对。**

你的想法有商业逻辑：**同一项服务对大额交易可能具有更高价值，可以通过价值收费，让大客户为网络承担更多成本，也让服务者获得利润。**

但综合你的目标——开放网络、微支付、高频结算、普通设备贡献资源——**我不建议把“所有原生转账一律收1%、不设上限”作为基础规则。更适合的是：基础执行费覆盖资源与共同安全成本；实际提供的支付、兑换、担保等增值服务，可以另按金额收费。**

下面先说明判断，再给出五类业务的成本核算表。

## 一、先纠正一个前提：银行并不普遍按转账金额收1%

我查到的官方实例，收费结构其实很多样：

- **工商银行个人网银**的公开说明采用分档收费；大于5万元的部分规则为按汇款金额的 **0.015%** 收取，但有**每笔25元上限**。适用优惠、渠道和当地规则另有说明，并不是无上限1%。[工商银行](https://wap.icbc.com.cn/icbc/%E7%83%AD%E7%82%B9%E7%AD%94%E7%96%91/%E4%B8%AA%E4%BA%BA%E9%87%91%E8%9E%8D/%E7%BD%91%E4%B8%8A%E9%93%B6%E8%A1%8C%E8%BD%AC%E8%B4%A6%E6%B1%87%E6%AC%BE%E6%89%8B%E7%BB%AD%E8%B4%B9%E5%A6%82%E4%BD%95%E6%94%B6%E5%8F%96.htm?utm_source=chatgpt.com)
- **Stripe美国标准定价**中，银行卡收款为 **2.9%＋0.30美元**，ACH Direct Debit则为 **0.8%、最高5美元**。这两项是不同支付服务，不能简单当成同一种银行转账成本。[Stripe](https://stripe.com/pricing?locale=en-US\&utm_source=chatgpt.com)

所以值得借鉴的不是某个百分比，而是：

> **不同服务承担不同工作和责任，因此可以采用固定费、百分比、最低费、封顶、订阅或组合收费。**

你的NOVOVM也应该这样分，而不是要求所有业务只有一种价格公式。

## 二、按金额收费有什么好处？你的判断有一部分很有价值

### 1. 成本相近，不代表售价必须相同

假设同样是一次合法转账，处理10 NOV和10万NOV的资源消耗接近。这个事实只能说明**计算成本接近**，不能推导出服务商只能收取相同价格、更不能只能收回电费。

商业价格还可以包含合理利润、持续维护、备用容量、公共安全预算，以及客户愿意购买的附加服务。

你的原计费契约也不是“所有节点必须按成本价营业”，而是**节点自主报价，客户选择，明确用户总支出和提供者净收入**。因此，资源计量和盈利并不冲突。

### 2. 大额交易可以购买更高责任的服务

例如，客户购买的不只是余额转移，还包括额外证明、专门审计、限时服务承诺、实际兑换流动性，或者有明确责任和资金支持的赔偿安排。

**这时按金额收取一部分费用，可以有依据。**尤其当提供者实际承担的资金占用或赔偿责任随金额增加时，不能只用CPU微秒来解释全部价格。

但需要区分：

**“网络保护着大额资产”是系统安全问题；“某服务商承担这笔交易的赔偿责任”是具体服务合同。**不能仅因为金额大，就声称每个转发节点承担了等额金融风险。

### 3. 可以用高价值业务支持公共网络

这也是一种可以讨论的经济选择。但应该公开说明它是**网络公共资金贡献或服务溢价**，而不是把它伪装成实际消耗了更多计算、带宽。

**谁付多少，与谁获得多少，是两项规则。**即使大额业务支付了较高费用，也不能自动得出“刚好接到这笔交易的节点独占全部费用”。

## 三、为什么我仍不建议基础转账统一收1%？

### 1. 对经常流转的资金，1%并不小

纯算术如下，不包含其他费用：

| 转账金额 | 按1%收费 |
|---|---:|
| 10 NOV | 0.1 NOV |
| 1,000 NOV | 10 NOV |
| 100,000 NOV | 1,000 NOV |
| 1,000,000 NOV | 10,000 NOV |

再假设同一笔本金每次转移都从本金扣除1%，没有其他收入：

\[
100\times0.99^{10}\approx90.44
\]

转移10次后，原100 NOV剩约90.44 NOV；转移100次后剩约36.60 NOV。**这些币不是被销毁，而是大量转给了收费方。**

对于你的节点日结、交易所资金调度、应用支付、用户资源消费，这会形成一个问题：

> **资金越频繁用于真实经济活动，承担的累计比例费用越高。**

这不必然使业务失败，但与“低摩擦的通用结算基础设施”存在明显张力。

### 2. 费率提高，不代表总收入一定提高

这里应看：

\[
\text{按额收费收入}=r\times V(r)
\]

其中，\(r\)是费率，\(V(r)\)是**这个费率下真正愿意使用网络的结算金额**，不是假设所有客户完全不受价格影响的固定数。

例如，纯假设：

- 1%费率下，实际结算额为100万，收入为1万；
- 0.1%费率下，实际结算额为2,000万，收入为2万。

也可能相反。**哪个更好，需要真实需求数据，不能单靠“单笔赚得更多”判断。**

我的商业判断是：对你希望吸引的大额、高频、资金周转型用户，无上限1%很可能成为明显的使用阻力；这是一项需要验证的市场风险，不是已经测得的用户流失比例。

### 3. 只按金额收费，覆盖不了低金额、高资源消耗

一个低金额请求，仍可能需要大量计算、写入或证明。甚至某些程序执行根本没有“转账金额”，但会占用很多资源。

所以，即使采用按额收费，**资源限制和资源基础费仍然不能删除**。以太坊的Gas也是为了计量执行工作、防止无界计算，而不是按转账金额衡量资源。[ethereum.org](https://ethereum.org/developers/docs/gas/?utm_source=chatgpt.com)

### 4. “大额交易给节点惊喜”，不一定对小节点有利

这是我对激励机制的判断：

如果某一笔大额交易的高费用主要归接入者或处理者，节点就会更有动力争抢大额订单，而不是稳定服务大量小用户。普通家庭节点未必拥有抢单、连接和持续在线优势。

**对小节点更有帮助的，是可预测的合格任务收入、合理利润和低成本结算，而不是偶尔抢中一笔高额手续费。**

你的经济契约也已经把收益依据放在实际履约，而不是在线、身份数量或重复回执上。

### 5. 统一按金额收费，还会遇到隐私、多资产和重复征费问题

如果某些资产金额是隐私保护的，协议要按金额收费，就需要证明费用计算正确，不能为收费强迫公开金额。

如果转的是nETH、其他资产，而费用必须用NOV支付，还要明确资产估值、价格有效期及用户授权上限，不能简单把各种资产的数量乘1%。

另外，用户购买订阅、通讯池向服务者结算、服务者转入自己的储蓄账户，如果每次都扣1%，就会反复减少同一笔服务资金。你的原契约已明确：**充值、余额结转和收入到账不是再次分账的理由。**

补充一个容易混淆的地方：**纯线性1%本身不会因为拆成十笔就变便宜。**真正容易产生绕行激励的是免额、费率跳档和封顶等设计；这些都需要单独测算，不能只加一个“封顶”就认为问题全部解决。

## 四、我对NOVOVM的推荐：基础执行与增值服务分开定价

建议采用下面的结构，**这是本次分析建议，不是已经批准的费率**：

\[
\boxed{
\text{用户总费用}
=
\text{基础Execution Fee}
+
\text{用户明确购买的增值服务费}
}
\]

**基础Execution Fee：**按确定性资源工作量、必要状态保存和共同确认成本制定，包含合理经营空间。普通转账不因为金额大就默认抽走1%。

**增值服务费：**实际购买收款处理、兑换、商户对账、额外证明、限时保障等服务时，可以按笔、按月、按金额或组合收费。服务责任、价格、上限和收款方事先明确。

例如，某项增值服务可以研究：

\[
F_{\mathrm{增值}}=\min(rV,\ F_{\max})
\]

但这里的\(r\)、\(F_{\max}\)必须来自服务价值、成本和市场验证，不宜现在随手定成1%。

**若你的目标是让每笔大额原生转账都额外支持网络，也可以设计公开的按额附加费；但那应被明确记录为一项新的经济政策，而不是现有资源费的自然推论。**你现有文档规定原生费用按`compute + storage + bandwidth + proof + routing`分项核算，改变它需要显式修订，而不能悄悄混入。

我的优先推荐仍是：**普通转账保持资源型基础费；高价值金融服务在业务层定价。既给大客户购买更好服务的空间，也不让所有NOV流转都承担金融服务佣金。**

## 五、五类业务的实际资源成本表，应该这样建立

**成本表不是最终价目表。**它先回答“完成一项服务花了多少资源”，再决定报价、利润和分配。

在我此次核对的材料中，**转账已有部分历史CPU实测；五类业务尚没有同一版本、同一计量边界下的完整成本数据，更没有完整货币成本。**因此下面明确列出实测对象和缺项，不给未知成本编数字。

### 1. 业务成本总表

以下样本是建议的测量基准，不是默认套餐或生产限额。

| 业务 | 标准测量对象 | 需要记录的实际资源 | 成本成立的终点 | 当前需要补齐 |
|---|---|---|---|---|
| **UCA登记** | 一次真实登记；基本记录与附加字段分别测 | 认证与执行CPU；规范输入／输出字节；新增逻辑状态；实际数据库写入；索引、日志及约定保存责任 | 登记最终确认，可查询，重启后仍一致 | 每条记录真实大小、保存范围及周期、完整登记成本 |
| **原生转账** | 同账户条件下改变金额；既有收款账户、新收款账户、业务失败分别测 | 必要参与节点的CPU/GPU工作；实际网络字节；状态读写；日志与回执保存；启用时的证明成本 | 唯一交易最终结果、账务及费用一致 | 在当前合格制品和真实拓扑上统一复测；现金成本标定 |
| **寄存投递** | 小文本与1 MiB密文分别测；例如3副本、24小时上限 | 上传、复制、领取的实际字节；实际保管字节·秒；认证、查找、去重和回执CPU；失败替代成本 | 约定阶段履约、必要持久回执及应付核销 | 原TTL、副本、领取与回执的一次完整服务成本 |
| **内容分发** | 例如1 GiB内容、3副本保存30天；实际下载次数分开 | 初次分发；保管字节·秒；真实下载量；缓存命中；修复流量；校验和目录维护 | 内容可验证交付；保存责任按区间履行 | 不同热度、地域、缓存命中及设备利用率的成本 |
| **程序执行** | 发布与调用分开；固定输入的CPU任务、GPU任务、有／无证明分别测 | 规范执行单位；实际CPU/GPU时间；内存占用；状态读写；输入输出；代码保管；证明生成和验证 | 合同规定的结果／状态／证明被验证，必要时最终确认 | 当前实际可用入口的端到端数据；未接通的标为未接通 |

这里的字节、字节·秒、服务凭证和幂等结算，沿用你原契约。**传输ACK不等于设备持久收件，接受保管也不等于已完成整个TTL的保管责任。**

### 2. 已有转账数据可以用，但只能作历史基线

仓库这份历史报告记录过：

| 历史轮次 | 四节点CPU合计／唯一成功交易 | 客户端驱动CPU／交易 |
|---|---:|---:|
| CPU验签第一轮 | 2,236.60 µs | 513.55 µs |
| GPU验签轮 | 2,024.65 µs | 513.32 µs |
| CPU验签重复轮 | 2,377.03 µs | 581.98 µs |

它统计的是四个节点的**进程CPU时间合计**，不是每个节点各用这么多；GPU轮也没有计入GPU设备时间和能耗。报告还明确排除了部分准备、后续审计和冷恢复。

以第一轮作纯单位换算：

\[
100万笔\times2,236.60\ \mu s
\approx0.6213\ \text{CPU核小时}
\]

**这只是该历史负载下的一项计算资源量，不是100万笔交易的总成本。**还缺网络、存储、闲置容量、运维等，更不能直接外推为当前四机或正式网络的报价。

客户端自己签名的成本也不应默认向网络服务者付款；只有客户端明确购买了对应服务，才进入相应账单。

### 3. 存储和流量先统一单位，不能混算

两个简单例子：

- 1 MiB数据、3份副本、实际保存24小时：

\[
\frac{1}{1024}\times3\times24
=0.0703125\ \mathrm{GiB\cdot小时}
\]

- 1 GiB内容、3份副本、保存30天：

\[
1\times3\times30\times24
=2,160\ \mathrm{GiB\cdot小时}
\]

若第二项又发生100次完整1 GiB下载，则另有100 GiB实际交付，不能与保管量混成一个“流量”。

**副本数已经包含在实际物理保管量里时，不能再乘一次副本数。**同样，普通重传是真实经营成本，但原合同不允许把每次重传当成新的用户订单收费；应通过合理报价和可靠性预算覆盖。

## 六、资源量怎样变成货币成本？

建议对每种设备／服务条件建立单位成本，而不是用同一个云服务器价格套所有家用节点。

| 成本项 | 核算依据 | 特别注意 |
|---|---|---|
| **CPU／GPU** | 租赁费用，或设备折旧、电费与维护；结合实际可服务时间和有效利用率 | 云实例费用已含硬件和电力时，不再另加同一份成本 |
| **内存** | 占用量×占用时间，以及所需常驻容量的分摊 | 不能只算任务运行时，忽略必须常驻的工作集 |
| **持久存储** | 可用容量、保存时长、冗余、写放大、介质损耗和维护 | 逻辑1 GiB不等于物理只占1 GiB；永久保存承诺不能拿一天成本估算 |
| **网络** | 实际链路资费、有效出入流量、占用时段及容量 | 家宽包月与云按流量收费分开；入站、出站不机械双收 |
| **发现、确认与公共维护** | 必要且有界的基础服务、空闲保活和安全运行预算 | 不按全网节点总数无限乘算，不允许节点自增副本扩大账单 |
| **结算、失败与替代服务** | 批量核销、必要重试、恢复、正常故障替代的实测 | 区分已发生成本与未来责任准备，不能把同一风险预算记两遍 |

建议同时给出两种成本：

**增量成本**：已有设备完成新增服务额外增加的成本。

**完全成本**：再加设备折旧、正常闲置、维护与必要备用容量的合理分摊。

前者有助于用户决定“闲置电脑要不要共享”；后者用于判断“长期专业经营能不能持续”。**不能按设备永远100%满载计算低价，也不能让客户支付某节点任意低效率带来的全部成本。**

因此，实测CPU时间用于成本标定；正式链上收费仍应使用统一、可验证的资源规则。普通服务市场则按已接受报价结算，不能由节点事后自报“我跑得慢，所以多收钱”。这也符合原契约的报价绑定与禁止追溯提价原则。

## 七、怎样从成本表定出“用户愿意付、节点又能赚钱”的价格？

### 1. 节点利润必须显式留出来

假设某批服务的提供者完全成本为 \(C\)，希望获得提供者收入口径下的毛利率 \(m\)，那么目标净收为：

\[
I_{\mathrm{提供者}}=\frac{C}{1-m}
\]

如果该业务还存在明确的网络用途分区比例 \(s\)，则对应用户总价模型为：

\[
F_{\mathrm{用户}}=\frac{C}{(1-m)(1-s)}
\]

这是定价模型，不是保证利润的协议承诺。

例如，**仅作算术演示**：某批聊天服务提供者成本30元，目标毛利率25%，使用已确认的订阅20%网络用途分区：

\[
F_{\mathrm{用户}}=\frac{30}{0.75\times0.8}=50元
\]

其中提供者得到40元，成本30元、毛利10元；网络用途10元仍需承担自己的职责，**不是10元全部成为利润**。

这里的80/20只适用于你的订阅事件，不能自动套到原生转账或其他业务。

### 2. 再用需求和竞争验证，而不是只做成本加成

成本表告诉你“这个报价能否持续”，但不保证客户接受。

因此，每类业务还需要同时观察：有效订单量、复购、满载程度、不同质量档位的购买意愿，以及高价是否减少真实使用。**能带来更多稳定任务的合理利润率，往往比一笔订单的极高毛利更有利于普通节点——这是我的经营判断，应以实际业务数据检验。**

### 3. 最后形成NOV报价，而不是每条请求临时查汇率

节点或协议按批准的定价机制形成**有版本、有期限、有最高扣款的NOV报价**；用户接受后按该报价执行，不追溯改价。

成本账可以使用本币作分析，但不能让不同验证节点各自读取实时外汇或NOV价格、算出不同的账本扣款。普通消息热路径也不应反复查链、查汇率。

## 我的最终判断

**你的方向不是错的：网络应该获取合理的商业价值，而不是只报销电费，大客户也完全可以贡献更多收入。**

但要选对收费对象：

> **基础转账卖的是可验证的执行与结算；增值支付服务卖的是额外能力与责任；存储、通信和内容分发卖的是实际资源服务。它们可以有不同的价格模型。**

因此，我建议暂不冻结“全体转账1%”，也暂不冻结此前的0.00001 NOV和90/10。先沿已有程序和计量接口，形成上面五类业务的**资源实测量＋单位成本＋提供者目标净收＋用户报价**。已有入口就测，未接通的明确标缺项，不为填表另造引擎或开启一轮全量CI。

**成本表负责说明钱怎么花，定价规则负责决定客户付多少，分账规则负责决定谁得到多少。把这三件事分清，你才能既让小节点赚钱，又不把NOVONET做成资金每流转一次就被抽走一大截的网络。**
````
